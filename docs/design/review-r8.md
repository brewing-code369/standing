## Questions

1. Designed product or styled document? A designed product on all four routes. The line card, inline refusal codes with Try it, the receipt and the key rows are built from the content.
2. Primary job obvious in 3 s? Home, yes at both widths: the count with "each pull inside its cap", then the claim, then two buttons (`r8-1440.png`, `r8-390.png`). Member, yes: "Active", 159 renewals, the countdown. Checkout, mostly: the title leads, but at 390 the first action is below the fold of a short phone.
3. Would a competent practitioner produce exactly this without the content? No for the line card, refusal codes, receipt and key rows. Yes only for the uppercase-label texture.
4. Does "next renewal" mean the next pull? No. It counts to `periodEnd`. In `member-390.png` the card shows "LEFT THIS PERIOD 0.80 of 0.80", a full yellow bar, "next renewal in 4m 03s", and still 159 renewals with the latest row at 11:48:56. That is the 1440 count, captured when the same countdown read "in 54s". So the 11:53:56 period ended without a new row at that moment, and the pull lands some time after the countdown reaches zero. A judge watching the countdown expire will see nothing happen.

## Three highest-leverage fixes

1. Make the overcut receipt argue one cause, once. Retitle it "Platform key pulls 0.38 after its 0.19 cap is spent". Add a "Left this period 0.00 pathUSD" row and make that the red row, with Asked in ink. Drop the subline, because the footer already says "This key already pulled its cap for the period". Delete `.overshoot*` from `styles.css:565-568`. Set the title address in mono. Pick the cheat member from the plan or runner rather than the ledger so the button is live at first paint.
2. Tie the countdown to the pull, not the period. Label it "period ends in 54s", or count to the runner's next scheduled tick for this member. Add a "due now · waiting for the runner" state that holds until the new history row appears and the renewal count increments. Give the runner footer an amber "last ticked 2m ago" state for staleness, and keep red for "not answering" after 3 failures.
3. Finish the outsider row and the 390 checkout. Give the outsider refusal its actual chain error name, mono and red, in the same `└ ✕ label Code Try it` component the lines use, so all four pressable refusals look alike. On `/p/...` at 390, move the split sentence below the panel header (or into the line card) so "Use a browser key" lands above y = 400. Collapse home ledger rows at 390 to one line per pull (`0.80 creator · 0x65bc…`), so a renewal is about 120px rather than 290px.

## Numbers that look invented

- "1,434 capped pulls settled" (478 × 3), "1,437" (479 × 3), "1,428" (476 × 3) are still `complete * 3` (`Home.tsx:126`). The sentence says "settled, read through block …" as though the logs were counted. Every visible ledger row is 3 OF 3 SETTLED, so it is not wrong in these captures, but it is not a read. The ledger footer phrasing ("three pulls each") is the honest version; use it in the hero too.
- "Next renewal in 54s" / "in 4m 03s" is `periodEnd - now`, not the time of the next pull (Question 4). The number is a real period boundary presented as a payment time.
- Home receipt "Asked 0.38" in red still implies the excess caused the refusal. The subline now states the true cause (0.00 left). The emphasis contradicts it.
- Verified and consistent: 478 × 3 = 1,434; 479 × 3 = 1,437; 476 × 3 = 1,428. Receipt blocks are later than their page's head block (39,234,987 > 39,234,977 at 1440; 39,234,681 > 39,234,671 at 390). Member 159 renewals = 159.00 pathUSD at 1.00 each. Member history rows are exactly 5 minutes apart (11:48:56 … 11:23:56). Home interleaves three members on their own 5-minute cadences (0xEaD1 11:49:10 / 11:44:10, 0x27DB 11:49:04 / 11:44:04, 0xC18a 11:48:56 / 11:43:56). The 0xC18a 11:48:56 row carries 0x46b238…169093 on both `/` and `/m/...`, so the two routes read the same logs. Per-row 0.80 + 0.19 + 0.01 = 1.00. In `member-full-1440.png`, LEFT THIS PERIOD 0.00 of cap matches full black bars, and PERIOD RESETS "in 54s" equals next renewal "in 54s". `/new` preview 8.00 / 1.90 / 0.10 = 10.00 at 20% cut, with the 1% fee taken from the platform side, as the footnote states. The redirect receipt (`member-try-1440.png`) shows Asked 0.19 = Cap 0.19, and the stated cause is CallNotAllowed (wrong recipient), which is right.
