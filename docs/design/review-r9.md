## Questions

1. Designed product or styled document? Designed product on all four routes. Unchanged from r8.
2. Primary job obvious in 3 s? Home: yes at both widths (`r9-1440.png`, `r9-390.png`). Member: yes, "Active" plus the period countdown. Checkout: at 1440 yes, at 390 the first action is still below a short phone's fold.
3. Would a competent practitioner produce exactly this without the content? No for the line card, receipt and key rows. Yes for the uppercase-label texture.
4. Was r8's "the pull lands after the countdown" finding right? No, and I retract it. Ledger rows are stamped with `row.periodEnd` (`receipts.tsx:30`, column header "PERIOD ENDING"), not the pull time. At 11:54:47 the member's latest row reads 11:58:56 and the countdown reads 4m 10s, which ends at 11:58:57: the current period was already paid at its start. At 11:56:15 the countdown reads 2m 41s, same end. The r9 relabel ("until the period ends") is accurate. The cost of this design: a "Latest renewals" table whose top row carries a time four minutes in the future reads like a bug to anyone who misses the column header.
5. Is the home cheat receipt true for the member it picks? Not always. The cheat targets `renewals[0].member` (`Home.tsx:105`). At 11:54:20 that was 0xEaD1, whose latest row reads "period ending 11:54:10" with no 11:59:10 row yet at 11:54:39 (`home-full-1440.png`). Its new period had started 10 s before the attempt and the runner had not pulled. If the key's period aligns with the memo period (which the member card's "PERIOD RESETS" equal to the row's period end implies), that key had 0.19 left, and 0.38 was refused because it exceeds 0.19, not because 0.00 was left. The r9 receipt would then print a red "Left this period 0.00" that is false. The 390 attempt (0xC18a at 11:54:30, pulled at about 11:53:56) is the case where 0.00 is true.

## Three highest-leverage fixes

1. Make "Left this period" a read. Have `/api/attack` return the key's remaining limit at the checked block (the same source as `state.remaining` in `wires.tsx:56`) and render that. Branch the title and footer on it: remaining 0 gives "pulls 0.38 after its 0.19 cap is spent"; remaining 0.19 gives "asks 0.38, twice what the key has left". Put the receipt's red on whichever row is the true cause. Pick the cheat member from the plan or runner, not the ledger, so the button is live at first paint and the target is a member whose period has already been pulled.
2. Stop painting a single failed poll red. In `App.tsx:20` keep `null` (grey "Reading the renewal runner") on a first failure and only go to `'down'` after 3 consecutive failures, as the r7 fix intended. Then re-capture `member-390.png` and confirm the footer matches the body. Add the missing `member-try-1440.png` (outsider Try it) and confirm the response's `reason` is literally `KeyNotFound`; render `tryRes.reason` rather than the JSX constant.
3. Do the 390 work that has now slipped two rounds. On `/p/...` move the split sentence into the panel or below its header so "Use a browser key" lands above y = 400. Collapse each home ledger renewal at 390 to one line per pull (`0.80 creator · 0x3ac7…`), bringing a renewal from about 290 px to about 120 px. Render the outsider refusal with the same `└ ✕ label Code Try it` row as the lines, so it stays on one line at 390. Show the pull time beside "Period ending" or label the top row "this period, paid" so a future timestamp does not read as an error.

## Numbers that look invented

- "Left this period 0.00 pathUSD" is a literal (`refusal.tsx:34`) shown for every SpendingLimitExceeded. The member card computes the same quantity from chain; the receipt does not. Question 5 shows a plausible attempt where it is false.
- "1,446 capped pulls settled" (482 × 3), "1,440" (480 × 3), "1,437" (479 × 3) are `complete * 3` (`Home.tsx:126`; the server computes `pulls: complete * 3` too). Not wrong in any capture, since every visible row is 3 OF 3 SETTLED, but it is a derivation written as a read. The ledger footer ("480 complete renewals, three pulls each") is the honest phrasing.
- "KeyNotFound" on the outsider row is a JSX constant (`Member.tsx:193`). The server attack builds a fresh random address and lets `refusalName` classify whatever the node returns (`server/index.ts:223-225`), which could as well be `Unauthorized` or `InsufficientBalance`. Unverified this round: the Try it capture is missing.
- Verified and consistent: 480 × 3 = 1,440; 482 × 3 = 1,446; 479 × 3 = 1,437. Member 161 renewals = 161.00 pathUSD at 1.00 each, same on both member captures. Member history rows are exactly 5 minutes apart (11:58:56 … 11:33:56). The 0xC18a rows on home (11:58:56 0x3ac7c5…2faacb, 11:53:56 0x783913…0a8841) carry the same hashes as on `/m/...`, so both routes read the same logs. Countdown 4m 10s at 11:54:47 and 2m 41s at 11:56:15 both end at 11:58:56/57, matching the top row's period end and "PERIOD RESETS". LEFT THIS PERIOD 0.00 of 0.80 / 0.19 / 0.01 matches the full black bars. Receipt blocks (39,235,374 at 390) are later than the hero head (39,235,364) on the same capture. `/new` preview 8.00 / 1.90 / 0.10 = 10.00 at a 20% cut with the 1% fee from the platform side, as the footnote says.
